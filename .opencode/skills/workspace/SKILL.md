# Workspace maintenance routing

Workspace Maintainer owns workspace-level structure whether reusable or intentionally project-specific. Developer owns actual project implementation/content; Dual remains the default substantive Developer route.

Use `small-maintainer` for easy bounded workspace work and `heavy-maintainer` for difficult, subtle, important or risky bounded workspace work. They are capacity variants of one role, not separate workflows. Target worktree does not change identity.

Give the selected maintainer the exact `workspace` runtime ref, one explicit verified target, bounded outcome/scope, material constraints, required checks, publication requirement and expected evidence. Target instructions are evidence/output constraints, not a replacement maintenance workflow. `main` is never a Workspace Maintainer mutation target.

Ordinary workspace work does not require a package. For explicit package/transfer/source-lock work, require `change-package`. Current package identities are `workspace`, `developer`, and `orchestration`; historical package schemas may retain old names as compatibility evidence.

Review exact resulting refs/ranges, requested behavior, preserved project implementation/content, checks, durable truth and publication evidence. A project-specific workspace change does not automatically become reusable template behavior.
