# Web orchestration workflow

## Trigger

Use for ordinary repository research, task and outcome design, route selection,
implementation orchestration, review, steering, and completion.

## Establish the outcome

Resolve the requested observable outcome, success evidence, material scope,
constraints, and human-owned decisions. Re-establish exact remote refs before
relying on supplied SHAs or old records. Use public web research when it improves
the decision, and distinguish target-repository evidence from external prior art.

Use the smallest evidence set that supports a sound decision. Tiny one-turn work
does not need a durable record or delegated research merely to fit a workflow.

For consequential work where durable authority helps, create or resume exactly
one canonical task record containing the accepted outcome, scope, constraints,
required outputs and checks, accepted design, and explicit exceptions. Create
separate concise task progress only when another session needs resumable state.
Progress never changes or duplicates the task plan.

## Select one route

Choose from the work itself, not from a retry ladder:

- **Direct web/GitHub:** a tiny, exact, low-risk remote change whose paths and
  edits are already known.
- **Maintenance:** bounded repository or template maintenance that fits the
  template-development-rooted maintenance runtime. Choose `small-maintainer` for
  easy work or `heavy-maintainer` for difficult, subtle, important, or risky
  bounded work, then load `skill-maintenance.md`.
- **Small developer:** `small-developer` for very simple bounded implementation.
- **Heavy developer:** `heavy-developer` for difficult or subtle implementation
  that still fits one bounded developer session.
- **Dual developer:** the default for substantive development with interacting
  edits, nontrivial implementation, meaningful tests, or deeper architecture.

Small, heavy, maintenance, and Dual are independent routes. They are not retries
or escalation levels. Never replace Spark with another route inside Dual. Keep
one mutating route active.

Before mutation, establish the exact target branch and start SHA. Read only the
task records, AS-BUILT, deviations, architecture, actionable docs, and affected
code needed to constrain the route.

## Execute and review

For direct work, re-read the exact remote ref immediately before writing. Keep the
change within the known tiny scope and read back the resulting ref, files, and
range. Stop and reconcile unexpected movement or an ambiguous write.

For a bounded developer route, provide one outcome, exact useful start state,
scope limits, material constraints, durable-truth obligations, useful checks, and
expected observable result. The developer owns implementation inside that route.
Review the exact resulting range directly because there is no separate Lead.

For Dual, give Lead the accepted outcome or task record, exact Git start state,
material constraints, and relevant durable records. Lead is the developer brain:
it inspects current implementation, chooses the concrete architecture, directs
Spark, reviews the repository diff and checks, and steers corrections. Do not
duplicate that analysis at the Web layer or prescribe a second Lead/Spark
protocol. Do not require Spark to transmit material the Lead can inspect directly.

Treat all handoffs as evidence. Resolve ordinary ambiguity from repository state
before asking the human. Ask only for a real human-owned decision, unavailable
required capability, or external blocker.

## Durable truth and completion

Before accepting a changed result, verify the exact remote range, requested
behavior, relevant checks, compatibility and safety boundaries, and applicable
durable truth. AS-BUILT must remain complete enough to reconstruct current
implementation in its scope. A formal deviation is needed only for material final
divergence from an applicable accepted expectation. Do not create documentation,
packages, snapshots, archival, or extra validation merely as completion ceremony.

Completion requires exact evidence for the requested outcome, reconciliation of
every launched mutation, and a clear statement of any remaining material risk or
human decision. Promotion is a separate exact-SHA procedure.
