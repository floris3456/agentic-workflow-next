# Task design

## Trigger

Load before creating or materially revising a delegated implementation task.

## Procedure

1. Start from the human goal and exact remote evidence.
2. Assign one stable task ID compatible with repository conventions.
3. Define one observable general outcome. A materially different outcome requires a new task.
4. Identify the task-start `developer` SHA.
5. State scope, constraints, required records, checks, and stop conditions.
6. Include this exact five-field response contract: `Status:`, `Files changed:`, `Checks + perceived results:`, `Blockers/decisions:`, and `Task record:`.
7. Require task-progress before substantive work and preservation of the public-safe brief.
8. Require AS-BUILT and deviations to change atomically with implementation facts they describe.
9. State immutable evidence boundaries when relevant.
10. Remove private context, secrets, personal details, and sensitive values before delegation.
11. Prefer a bounded task Luna can complete; do not require Sol through avoidable ambiguity.

The brief must remain sufficient after chat compaction without irrelevant conversation history. Construct it independently, then embed it unchanged as `arguments.brief`; do not add the command UUID, sequence, issue metadata, or expected-SHA guard to the brief text.
