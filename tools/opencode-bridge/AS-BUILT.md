## Contract and transport

The bridge pins OpenCode and `@opencode-ai/sdk` `1.18.16`, upstream release commit `a3647eb025c7615159d417dcc49fc39fdaeba65b`, and live OpenAPI SHA-256 `c3a9f94af0c3324d97b482b14c692e810ce7ccac3136319ba46334de972b4cf1`. The generated manifest classifies all 188 released operations: 182 ordinary HTTP operations, four SSE operations, and two PTY WebSocket operations. It records method, path, transport, effect, and web policy. Offline manifest comparison reports added, removed, or routing-changed operations during an upgrade; runtime compatibility compares the live version and exact raw OpenAPI hash to this pinned manifest rather than comparing the manifest with itself.

`OpenCodeClient` rejects non-loopback or credential-bearing URLs, keeps Basic Auth internal, exposes the exact SDK for health, and serializes every HTTP operation from operation ID plus path/query/body arguments. It handles deep-object query values, JSON/text/diff/binary/empty responses, and the explicit `v2.fs.read` wildcard that upstream OpenAPI/SDK generation omits. SSE parsing is explicit and preserves CRLF semantics across arbitrary stream-chunk boundaries. PTY obtains one-use tickets, connects real WebSockets for either released prefix, persists cursor-addressed bounded output before advancing, supports input, and reconnects with fresh tickets.

Consequential OpenCode commands re-run live version/hash compatibility and fail closed on drift. Diagnostic reads remain available. API capability is independent of web policy.

## Durable recovery

`RecoveryCoordinator` combines legacy repository/workspace SSE, direct per-session v2 history/SSE, project sync history, event-ID deduplication, aggregate cursors, and focused canonical recovery for developer sessions. Pending `permission.list` and `question.list` entries for mapped developer sessions become stable task-correlated events; recovery republishes an existing entry through the idempotent outbox path so a crash after event persistence cannot strand the public interaction. Historical Scout recovery code and deterministic tests remain for durable-state compatibility, but the service does not contact an inspected-ref workspace or the normal OpenCode server for an old Scout mapping while the hardened runtime boundary is unavailable. Events enter SQLite before callbacks. For a mapped developer idle/error event, the event row, cursor, session state, and pending response delivery commit in the same transaction, so a stop before the callback cannot strand the handoff behind an advanced cursor. Reconnect loops use bounded exponential backoff and jitter. It does not send or claim standard SSE `Last-Event-ID`; an upstream transient event that is neither durable nor still pending in a canonical interaction list can remain unrecoverable after complete outage.

SQLite uses Node's built-in `node:sqlite` and requires Node `22.13.0` or newer. Configuration lexically confines the state file outside the tracked working tree or beneath its Git directory. The state loader requires an owner-only parent, rejects an existing final path that is a symlink or non-regular file, creates a mode `0700` parent, and normalizes the database to mode `0600`; it does not claim to reject symlinks in every ancestor component. SQLite enables WAL, full synchronization, foreign keys, and a busy timeout. Schema 3 stores command state/results and pre-ledger admission rejections, sequence-free recovery/Scout requests, task/developer-session/Scout-session and issue mappings, latest projected responses, response-delivery retries, public aliases, events/cursors, GitHub outbox/cache, compatibility, legacy reconciliation/sequence tables retained for existing databases, PTY metadata/output, and service health. Accepted `(task_id, sequence)` rows are the sole active sequence authority; admission derives the next value with `MAX(sequence)` inside the same immediate transaction and no longer reads or updates `task_sequences`. Command UUID and accepted task-sequence uniqueness are fail-closed. The first command sequence is exactly `1`, every later accepted sequence is contiguous, and no task admits another command while one is `accepted` or `applying`. Every authenticated parse-valid poller/admission rejection is durable without consuming sequence, including unbound or task-mismatched commands, the first-command rule, the one-open-mutating-issue gate, sequence/nonterminal checks, and missing/misplaced mandatory guards. An interrupted command or Scout start in `applying` becomes `indeterminate` on restart and is never reissued; an interrupted `command.status`, `task.status`, or `scout.status` is recomputed from local durable state under the same request UUID.

## GitHub control plane

The foreground service authenticates as a GitHub App by signed JWT, requests a one-repository installation token downscoped to Issues write and Contents read, rejects broader/insufficient returned permissions, caches until near expiry, and refreshes once after `401`. REST uses version `2026-03-10`, strictly parsed HTTPS-only credential-free API URLs, serial pagination with origin/loop limits, persisted ETags, and primary/secondary rate-limit timing. Public `api.github.com` derives `github.com`; an Enterprise `/api/v3` base derives its same host; any other supported custom API path requires explicit `github.git_host`, and a conflicting explicit host is rejected. Bootstrap parses only credential-free HTTPS, `ssh://git@`, or scp-style `git@host:` origins and exactly authenticates host plus case-insensitive owner/repository. Userinfo, suffix hosts, extra/malformed/encoded paths, unsupported schemes, and ambiguous host derivation fail closed.

Polling reads open labeled issues and comments only from exact configured authors with `OWNER`, `MEMBER`, or `COLLABORATOR` association. A task ID has one durable issue binding. Markers on a second issue that repeats an existing task ID receive bounded command/request rejections without changing the binding or aborting the poll cycle, so already accepted work and other issues continue. One open mapped mutating control issue serializes repository work. If persisted state and GitHub expose more than one, the bridge publishes one bounded diagnostic and freezes both new and restart-recovered command dispatch while sequence-free status requests remain available. The first command must be `start`; issue/task binding, UUID, sequence state, and every parse-valid pre-ledger rejection are durable. A stale marker rejected while another mutating issue is open therefore remains rejected after that issue closes; only a fresh UUID can be reconsidered. Polling is faster while a control issue is open and slower while idle. Sequence-free `command.status`, `task.status`, `scout.start`, and `scout.status` retain their own UUID ledger and never change task sequence, but current `scout.start` returns the explicit hardened-runtime failure without checking out or contacting OpenCode.

Bridge comments and label changes use a paced durable outbox. Comments carry deterministic dedupe markers, but only a marker authored by the configured App bot suppresses a retry. Status publication removes stale bridge-owned labels and adds one current label without replacing unrelated labels. `applying` is queued and attempted before its handler starts, so the durable and public lifecycle agree. Outbox completion can be reconstructed from terminal commands after restart.

## Commands and policy

`agentic-bridge/1` provides guarded start, status, steer, Luna/Sol route, permission reply, question reply, abort, bounded event pages, PTY create/input/read/resize/remove, finalization, synchronization recovery, exact-SHA promotion, and generic `opencode.request`. The Luna and Sol implementation agents explicitly allow OpenCode's structured question tool; a structured question event receives a task-bound public alias that `question.reply` resolves locally, whereas ordinary assistant text does not. A future Scout contract must deny interactions. Start and promotion require a clean synchronized `developer` checkout plus exact expected ref/SHA. Promotion is disabled by default and delegates to the existing guarded script only after the web orchestrator has received explicit human exact-SHA approval. PTY create/input/resize/remove are denied unless `policy.pty_enabled` is true; bounded cursor-based `pty.read` is a diagnostic local-state read and remains available.

`command.status` returns one task-correlated command's exact durable ledger or pre-ledger-rejection state, known public result/error, timestamps, `applying` age, and service heartbeat. `task.status` returns the mapped developer session state and latest projected developer response. These are reconciliation views rather than progress-consuming commands. If a restart interrupts one of the three local status request kinds, the bridge safely requeues and recomputes it under the same UUID; it never calls OpenCode or repeats a mutation to do so. A stuck or ambiguous mutation gets one bounded status reconciliation; it is never automatically retried. If local inspection and a current heartbeat cannot resolve the state, an operator stops/restarts the bridge, which converts durable command `applying` to `indeterminate` for evidence-based reconciliation.

`scout.start` still validates exactly four closed arguments and keeps UUID-idempotent concurrent request admission, task/request status correlation, and no-replay restart semantics. It now fails before workspace preparation or any OpenCode request with one explicit hardened-runtime diagnostic. The tracked `repository-scout` agent was removed, so an inspected ref cannot own the trusted model, instructions, permissions, tool definitions, or startup extensions and the normal developer server is never used as a fallback. Existing Scout mappings and response deliveries remain durable but are not contacted or advanced by an unsafe runtime; `scout.status` remains a local correlated read.

The workspace primitive is retained and hardened for a future independent runtime. Every Git operation strips inherited Git configuration variables, disables system/global config, disables hooks with command-scoped `core.hooksPath`, disables file transport, and disables credential prompts. It verifies remote ancestry, exact detached HEAD, all untracked state, private-root realpath containment, and every symlink target. A dirty, wrong-ref, branch-attached, unresolved-link, or escaping-link workspace is disposed with the same hook-disabled Git boundary and is never reused. Preparation remains serialized only around Git resource mutation, with same-ref calls deduplicated.

OpenCode `1.18.16` cannot meet the remaining boundary with its built-ins: `read` calls `Instruction.resolve` and attaches nearby repository instructions even when project config discovery is disabled, `read` unconditionally invokes LSP warm-up, and configuration initialization schedules package dependency installation for scanned configuration directories. A ref-owned tracked agent, isolated HOME alone, permissions, `--pure`, and disabling project config therefore do not prove no instruction injection, no process/package side effect, or realpath-safe reads. The live Scout contract excludes LSP, bootstrap/status report `scoutRuntimeReady: false` with the reason, and no weaker launch path exists. The required decision is whether to add a bridge-owned in-process read/glob/grep tool/runtime (or adopt a separately audited sandbox/runtime release).

Generic HTTP reads are available from the manifest. Expert mutations and local-secret operations require separate exact local allowlists; sharing remains blocked from web transport. State-changing PTY operations and promotion have independent default-deny switches. Generic requests accept only well-shaped path/query/wildcard/body transport fields, remain pinned to the bridge's configured project rather than caller-supplied directory/workspace/location routing, resolve task-owned local aliases, reject raw OpenCode IDs and absolute paths, and permit `secret_ref` only for local-secret operations.

`PublicProjection` maps private session/PTY/permission/question/message/workspace/event IDs, including IDs embedded in text and object keys, plus opaque semantic project IDs to globally unique durable aliases. Every task-bound alias kind, including workspace aliases, has per-task storage and resolution and cannot cross task ownership. For recognized OpenCode message parts it publishes only text parts; reasoning, tool, step, and unknown part classes remain local. Provider metadata and reasoning/encrypted-content fields are omitted. It also redacts sensitive fields and token-like text, replaces absolute/private paths, neutralizes active Markdown in comments, and bounds depth, collections, strings, and total bytes. Raw results/events remain local. Local-secret operations and their failure details publish only a safe local-TUI action or fixed non-sensitive error; detailed results remain local.

After a mapped developer session becomes idle or errors, one full-synchronous SQLite transaction commits the event, its durable cursor, mapped session state, and response-delivery record. The transport obtains current session messages, structurally selects the latest assistant message, applies the same public projection, stores that task-correlated projected value, and queues it to the bound issue. Retrieval or publication failure stays pending and retries idempotently. The bridge does not parse or semantically validate the response, determine workflow status, or decide whether review can begin.

Historical Scout idle/error rows and projected results retain their task/request/exact-ref schema for local status compatibility, but the service does not retrieve or publish new Scout output while the hardened runtime is unavailable. Developer agents return six concise fields: one of four explicit statuses, exact pushed handoff developer SHA or `none`, changed areas, checks/results, blockers/decisions, and task-record path. `completed` requires the handoff commit to be pushed; failed push is `blocked` with `none`.

## Configuration and operation

The strict schema-v1 JSON loader rejects unknown fields, requires config/password/private-key/secret files to have owner-only permissions with no group/other bits (`0600` is recommended), validates one unambiguous API/Git host/repository identity and minimum polling intervals, and keeps runtime values outside Git. `github.git_host` is accepted only where required for a custom API base. Each instance has a unique ID, loopback URL/port, state path, App installation mapping, and process lock. Stale locks are recoverable; live duplicate processes are refused. Heartbeat, errors, compatibility, command backlog, outbox backlog, and the Scout runtime boundary are available through status; bootstrap is nonzero while the Scout runtime is unavailable.

Normal developer OpenCode and the bridge remain separate portable foreground processes. `bootstrap-opencode-bridge.sh` installs/builds and verifies or creates developer prerequisites, reports the unavailable Scout boundary, and exits nonzero until that boundary is resolved; `--check` does not create labels/state. `opencode-attach.sh` passes credentials through child environment rather than command arguments and attaches the ordinary TUI to the normal developer server. No systemd, webhook, tunnel, self-hosted runner, public OpenCode listener, or custom ChatGPT MCP is required.

The template initializer repairs only complete-history, synchronized clean one-commit unrelated `main`/`developer` roots with matching author/committer identities, author/committer times, subject, and path/mode/type tree shape, plus no active task record. Branch-specific blobs may differ. It creates a local old-root backup ref, then one exact developer-tree-preserving child of main and a hook-validated exact `force-with-lease`. Correct ancestry no-ops; shallow, established, shared, dirty, unsynchronized, active-task, sync-failed, or otherwise ambiguous history is refused; `web-orchestration` is untouched.
