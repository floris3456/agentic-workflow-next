# AS-BUILT: OpenCode bridge

**Status:** Developer operation remains integrated; an explicit verified
template-development workspace route and the dedicated hardened Scout runtime
have separate durable routing/recovery/response boundaries and fail closed
independently when unavailable

## Contract and transport

The bridge pins OpenCode and `@opencode-ai/sdk` `1.18.16`, upstream release commit `a3647eb025c7615159d417dcc49fc39fdaeba65b`, and live OpenAPI SHA-256 `c3a9f94af0c3324d97b482b14c692e810ce7ccac3136319ba46334de972b4cf1`. The generated manifest classifies all 188 released operations: 182 ordinary HTTP operations, four SSE operations, and two PTY WebSocket operations. It records method, path, transport, effect, and web policy. Offline manifest comparison reports added, removed, or routing-changed operations during an upgrade; runtime compatibility compares the live version and exact raw OpenAPI hash to this pinned manifest rather than comparing the manifest with itself.

`OpenCodeClient` rejects non-loopback or credential-bearing URLs, keeps Basic Auth internal, exposes the exact SDK for health, and serializes every HTTP operation from operation ID plus path/query/body arguments. It handles deep-object query values, JSON/text/diff/binary/empty responses, and the explicit `v2.fs.read` wildcard that upstream OpenAPI/SDK generation omits. SSE parsing is explicit and preserves CRLF semantics across arbitrary stream-chunk boundaries. PTY obtains one-use tickets, connects real WebSockets for either released prefix, persists cursor-addressed bounded output before advancing, supports input, and reconnects with fresh tickets.

Consequential OpenCode commands re-run live version/hash compatibility and fail closed on drift. Diagnostic reads remain available. API capability is independent of web policy.

## Durable recovery

`RecoveryCoordinator` combines legacy repository/workspace SSE, direct per-session v2 history/SSE, project sync history, event-ID deduplication, aggregate cursors, and focused canonical recovery. Pending `permission.list` and `question.list` entries for mapped developer/workspace task sessions become stable task-correlated events; recovery republishes an existing entry through the idempotent outbox path so a crash after event persistence cannot strand the public interaction. Before a permission/question reply, it captures the exact mapped task session's activity timestamp and latest assistant-message completion evidence. After the reply it records a resolved interaction episode and proves both pending lists plus the mapped session's live status and activity. A changed post-reply activity timestamp or changed terminal assistant message returns clean without a nudge, including when OpenCode has already removed the completed session from `session.status`. An otherwise non-progressing observation is followed by a bounded one-second grace and a second proof; only stable live non-progress with no interactions can reach the at-most-one persisted same-session continuation claim. Missing or malformed baseline/post-reply evidence blocks recovery rather than nudging. The claim precedes delivery, so uncertain delivery is blocked and never replayed; public command results distinguish `clean`, `recovered`, `blocked`, and `already-recovered`. The nudge uses the existing agent and fixed directory of the mapped runtime and never starts or replaces a session. Developer recovery uses only the normal client; workspace recovery uses only the verified template-worktree client. Scout recovery first rejects historical `scout-worktrees` paths, then fully revalidates the mapped exact-tree snapshot and uses only a per-snapshot client for the distinct Scout endpoint. Events enter SQLite before callbacks. For mapped idle/error events, the event row, cursor, session state, and pending response delivery commit in the same transaction, so a stop before the callback cannot strand the handoff behind an advanced cursor. Reconnect loops use bounded exponential backoff and jitter. It does not send or claim standard SSE `Last-Event-ID`; an upstream transient event that is neither durable nor still pending in a canonical interaction list can remain unrecoverable after complete outage.

SQLite uses Node's built-in `node:sqlite` and requires Node `22.13.0` or newer. Configuration lexically confines the state file outside the tracked working tree or beneath its Git directory. The state loader requires an owner-only parent, rejects an existing final path that is a symlink or non-regular file, creates a mode `0700` parent, and normalizes the database to mode `0600`; it does not claim to reject symlinks in every ancestor component. SQLite enables WAL, full synchronization, foreign keys, and a busy timeout. Schema 5 stores command state/results and pre-ledger admission rejections, sequence-free recovery/Scout requests, task-session (developer/workspace), Scout-session, and issue mappings, resolved interaction episodes and one-shot continuation claims, latest projected responses, response-delivery retries, public aliases, events/cursors, GitHub outbox/cache, compatibility, legacy reconciliation/sequence tables retained for existing databases, PTY metadata/output, and service health. Accepted `(task_id, sequence)` rows are the sole active sequence authority; admission derives the next value with `MAX(sequence)` inside the same immediate transaction and no longer reads or updates `task_sequences`. Command UUID and accepted task-sequence uniqueness are fail-closed. The first command sequence is exactly `1`, every later accepted sequence is contiguous, and no task admits another command while one is `accepted` or `applying`. Every authenticated parse-valid poller/admission rejection is durable without consuming sequence, including unbound or task-mismatched commands, the first-command rule, the one-open-mutating-issue gate, sequence/nonterminal checks, and missing/misplaced mandatory guards. An interrupted command or Scout start in `applying` becomes `indeterminate` on restart and is never reissued; an interrupted `command.status`, `task.status`, or `scout.status` is recomputed from local durable state under the same request UUID.

## Lifecycle recovery correction

Each mapped task-session recovery observer on its persisted runtime first drains the durable history lane, then performs an idempotent canonical terminal proof. The proof reads the exact mapped session's pending permission/question lists, status, and messages; it accepts only inactive or idle status with a matching latest assistant message that has a positive completion timestamp and a non-tool terminal finish (or a structurally valid error), and fails closed for outstanding interaction, busy/retry/tool-calls, nonterminal, malformed, or unavailable evidence. Its deterministic per-completion canonical event is persisted through the existing atomic response-delivery path, so task session state becomes terminal before projection/publication and repeated recovery or restart cannot duplicate it. The proof never sends a prompt or creates, restarts, or reroutes a session.

After a mapped developer session has already delivered a terminal response, successful `steer`, `finalize`, and `route` prompt delivery atomically reactivates that exact task/session mapping to `starting`; route also stores its selected agent in the same update. Failed or unproven prompt delivery leaves the terminal state and agent unchanged. Reactivation preserves the prior projected response until a later terminal delivery replaces it. The service then re-enrolls the exact developer recovery observer. If the prior observer is still registered while finishing, one coalesced pending re-enrollment starts only after that promise leaves the registry; if it has already left, the new observer starts immediately. A duplicate already-recorded terminal event does not move a reactivated session back to terminal because only insertion of a new response-delivery record advances session state. A distinct later canonical completion therefore queues and publishes exactly once through the unchanged delivery/projection path.

After a Scout session is successfully mapped and prompted, `ScoutRuntime` invokes the service's idempotent recovery-enrollment callback immediately. The service reuses its request-keyed observer guard, while startup still enumerates and recovers historical mapped Scouts. New and historical Scout recovery continue to use only the revalidated exact snapshot and dedicated Scout endpoint.

## Workspace maintenance route

`workspace.start` is an independently valid first mutating command. It requires
only top-level `expected.template_development_sha` and
`expected.ref: template-development`; ordinary developer start/promotion guards
are unchanged. A bridge-owned resolver explicitly fetches that remote ref, parses
NUL-delimited registered-worktree inventory, requires exactly one non-stale real
template-development branch worktree, and verifies canonical roots, shared Git
common directory, exact configured GitHub repository identity, branch, inventory
HEAD, optional upstream, clean status, and fetched remote equality. Resolver
errors and all public projection omit the private path.

The service creates this runtime lazily, pins its OpenCode client directory and
agent to the verified worktree and `workspace-maintainer`, and registers the
private root with projection. SQLite schema version 5 stores a fail-closed
`developer` or `workspace` task-session kind; legacy rows migrate to
`developer`. Status, steer/finalize, generic operations, question/permission
replies, continuation proof/nudge, abort, durable/canonical recovery, and terminal
delivery select the same runtime from that durable kind. Global and per-session
recovery are kind-filtered. Restart re-proves the same registered worktree but
allows expected post-start dirt or advancement. Workspace route changes, bridge
PTYs, and main promotion are denied. The normal developer route and human
exact-SHA main authority are unchanged.

A tracked credentialed runtime smoke starts an exact caller-supplied OpenCode
`1.18.16` executable with a sterile temporary HOME/XDG state and only one
explicit private OpenAI credential source. Through the production bridge
executor, clients, state, recovery, projection, and response transport it checks
the template-development project root, fixed agent, actual tool/skill inventory
and effective denials, a bounded read-only developer operation, evidence-only
target instructions, meaningful tool progress, same-session continuation,
terminal delivery without private paths, and a separate normal developer route.
It leaves both source worktrees unchanged and never targets `main`.
OAuth mode retains OpenCode's bundled authentication integration inside that
sterile state; the live inventory must prove the expected provider connection,
and every tool or skill it introduces remains subject to the agent's effective
default-deny permission audit. API-key mode disables default plugins.

## GitHub control plane

The foreground service authenticates as a GitHub App by signed JWT, requests a one-repository installation token downscoped to Issues write and Contents read, rejects broader/insufficient returned permissions, caches until near expiry, and refreshes once after `401`. REST uses version `2026-03-10`, strictly parsed HTTPS-only credential-free API URLs, serial pagination with origin/loop limits, persisted ETags, and primary/secondary rate-limit timing. Explicit current or cached next links remain authoritative after `304`; when both are absent and the cached page exactly fills one validated `per_page`, the client probes the immediately following validated page so growth across exact page boundaries remains discoverable without disabling ETag reuse. Public `api.github.com` derives `github.com`; an Enterprise `/api/v3` base derives its same host; any other supported custom API path requires explicit `github.git_host`, and a conflicting explicit host is rejected. Bootstrap parses only credential-free HTTPS, `ssh://git@`, or scp-style `git@host:` origins and exactly authenticates host plus case-insensitive owner/repository. Userinfo, suffix hosts, extra/malformed/encoded paths, unsupported schemes, and ambiguous host derivation fail closed.

Polling reads open labeled issues and comments only from exact configured authors with `OWNER`, `MEMBER`, or `COLLABORATOR` association. A task ID has one durable issue binding. Markers on a second issue that repeats an existing task ID receive bounded command/request rejections without changing the binding or aborting the poll cycle, so already accepted work and other issues continue. One open mapped mutating control issue serializes repository work. If persisted state and GitHub expose more than one, the bridge publishes one bounded diagnostic and freezes both new and restart-recovered command dispatch while sequence-free status requests remain available. The first command must be either `start` or `workspace.start`; issue/task binding, UUID, sequence state, and every parse-valid pre-ledger rejection are durable. A stale marker rejected while another mutating issue is open therefore remains rejected after that issue closes; only a fresh UUID can be reconsidered. Polling is faster while a control issue is open and slower while idle. Each successful complete control poll stores `service.last_poll_at` and clears the prior transient poll error; local status exposes both values so current GitHub-loop reachability is distinguishable from stale failure history. Sequence-free `command.status`, `task.status`, `scout.start`, and `scout.status` retain their own UUID ledger and never change task sequence. Scout starts run concurrently through the dedicated endpoint after active contract proof and fail without developer-server fallback.

Bridge comments and label changes use a paced durable outbox. Comments carry deterministic dedupe markers, but only a marker authored by the configured App bot suppresses a retry. Status publication removes stale bridge-owned labels and adds one current label without replacing unrelated labels. `applying` is queued and attempted before its handler starts, so the durable and public lifecycle agree. Outbox completion can be reconstructed from terminal commands after restart.

## Commands and policy

`agentic-bridge/1` provides guarded start, status, steer, Luna/Sol route, permission reply, question reply, abort, bounded event pages, PTY create/input/read/resize/remove, finalization, synchronization recovery, exact-SHA promotion, and generic `opencode.request`. The Luna and Sol implementation agents explicitly allow OpenCode's structured question tool; a structured question event receives a task-bound public alias that `question.reply` resolves locally, whereas ordinary assistant text does not. Permission/question replies publish a public-safe `continuation_recovery` outcome so clean versus recovered completion is distinguishable. The Scout contract denies interactions. Developer start and promotion require a clean synchronized `developer` checkout plus exact expected ref/SHA. Workspace start has its separate exact template-development ref/SHA guard. Promotion is disabled by default and delegates to the existing guarded script only after the web orchestrator has received explicit human exact-SHA approval. PTY create/input/resize/remove are denied unless `policy.pty_enabled` is true; bounded cursor-based `pty.read` is a diagnostic local-state read and remains available.

`command.status` returns one task-correlated command's exact durable ledger or pre-ledger-rejection state, known public result/error, timestamps, `applying` age, and service heartbeat. `task.status` returns the mapped session kind/state and latest projected task response while retaining the developer-specific field for compatibility. These are reconciliation views rather than progress-consuming commands. If a restart interrupts one of the three local status request kinds, the bridge safely requeues and recomputes it under the same UUID; it never calls OpenCode or repeats a mutation to do so. A stuck or ambiguous mutation gets one bounded status reconciliation; it is never automatically retried. If local inspection and a current heartbeat cannot resolve the state, an operator stops/restarts the bridge, which converts durable command `applying` to `indeterminate` for evidence-based reconciliation.

`scout.start` validates exactly four closed arguments and keeps UUID-idempotent concurrent request admission, task/request status correlation, and no-replay restart semantics. It actively proves the installed runtime/endpoint contract, prepares an exact canonical snapshot, creates one `repository-scout` session on the separate endpoint, maps it before prompting, and sends the focused question/scope/evidence request under the trusted prompt. The tracked ref-owned agent remains absent; inspected content cannot own model, instructions, permissions, tools, or startup extensions. `scout.status` remains a local correlated read.

The snapshot manager strips inherited Git configuration variables, disables system/global config, hooks, file transport, and credential prompts, fetches canonical `origin/developer`, verifies requested-commit ancestry, and uses NUL-delimited `ls-tree` plus `cat-file` only. It rejects gitlinks, `.git`, malformed/oversized paths, unsupported modes, trees over 50,000 entries, blobs over 8 MiB, or snapshots over 128 MiB. Regular files are `0444` regardless of Git executable mode, directories `0555`, and symlinks preserve bounded UTF-8 target text. Reuse verifies private-root containment, every path/type/mode/blob hash, and absence of extras; tampering causes disposal/rebuild. Preparation serializes only snapshot mutation and deduplicates same-ref calls.

The approved runtime avoids unsafe OpenCode built-ins. Bootstrap copies a locked package outside `repository_root`, runs trusted installation of exact `opencode-ai` and `@opencode-ai/plugin` `1.18.16`, and recursively removes write bits from config/dependencies. Non-root Linux is the only supported host. Each runtime root has a derived sibling `<runtime>-persistence`: install/reinstall fully replaces runtime config/dependencies/HOME/cache/temp while preserving owner-private OpenCode data/state needed to reconnect mapped Scout sessions. Persistence root, data, state, and auth paths must be regular non-symlink structures outside repository/runtime containment; any nested symlink or unsupported entry fails closed. Persistent files are never HOME, XDG config/cache/temp, PATH, `OPENCODE_CONFIG_DIR`, plugin, or instruction authority. Launch passes an allowlist environment with runtime-owned sterile HOME/config/cache/tmp, persistent XDG data/state, separate Basic Auth, project config/default plugins/external skills/watchers/autocompaction/pruning disabled, managed-config discovery redirected to a nonexistent immutable-runtime path, LSP/formatter false, and no inherited proxy/token/config variables. Provider authentication is exactly one private API-key file exported as `OPENAI_API_KEY` or one filtered OpenAI-only OAuth document fixed at persistent `data/opencode/auth.json`; a legacy runtime-data path is accepted only to seed the persistent file when it is absent, after which refreshed persistent OAuth is authoritative. Installation and launch revalidate persistent OAuth shape, symlink status, and private mode; API-key mode removes stale OAuth during installation and refuses a later persistent OAuth file at launch. Read-only config makes OpenCode's package-dependency check return before package-manager execution. Model provider traffic remains intentional; Scout tools themselves expose no network/process API.

The exact Luna/high prompt is hashed by installed-source comparison and checked from live agent inventory. It treats all repository files including instructions as untrusted evidence. Agent permissions retain wildcard deny and allow only `scout_read`, `scout_glob`, and `scout_grep`; all built-in and dynamic inventory entries plus external access/interactions remain denied. The dependency-free tool implementation imports only filesystem/path and plugin schema APIs, never follows symlinks, checks lexical plus canonical containment, accepts bounded relative paths, skips binary/non-UTF-8/oversized grep inputs, and bounds traversal/results.

Generic HTTP reads are available from the manifest. Expert mutations and local-secret operations require separate exact local allowlists; sharing remains blocked from web transport. State-changing PTY operations and promotion have independent default-deny switches. Generic requests accept only well-shaped path/query/wildcard/body transport fields, remain pinned to the bridge's configured project rather than caller-supplied directory/workspace/location routing, resolve task-owned local aliases, reject raw OpenCode IDs and absolute paths, and permit `secret_ref` only for local-secret operations.

`PublicProjection` maps private session/PTY/permission/question/message/workspace/event IDs, including IDs embedded in text and object keys, plus opaque semantic project IDs to globally unique durable aliases. Every task-bound alias kind, including workspace aliases, has per-task storage and resolution and cannot cross task ownership. For recognized OpenCode message parts it publishes only text parts; reasoning, tool, step, and unknown part classes remain local. Provider metadata and reasoning/encrypted-content fields are omitted. It also redacts sensitive fields and token-like text, replaces absolute/private paths, neutralizes active Markdown in comments, and bounds depth, collections, strings, and total bytes. Raw results/events remain local. Local-secret operations and their failure details publish only a safe local-TUI action or fixed non-sensitive error; detailed results remain local.

After a mapped developer or workspace session becomes idle or errors, one full-synchronous SQLite transaction commits the event, its durable cursor, mapped session kind/state, and response-delivery record. The runtime-selected transport obtains current session messages, structurally selects the latest assistant message, applies the same public projection, stores that task-correlated projected value, and queues it to the bound issue. Retrieval or publication failure stays pending and retries idempotently. The bridge does not parse or semantically validate the response, determine workflow status, or decide whether review can begin.

Scout idle/error rows and projected results retain task/request/exact-ref correlation. The service uses separate Scout recovery and response clients and publishes only after snapshot/runtime validation; historical worktree paths fail closed. Developer agents return six concise fields: one of four explicit statuses, exact pushed handoff developer SHA or `none`, changed areas, checks/results, blockers/decisions, and task-record path. `completed` requires the handoff commit to be pushed; failed push is `blocked` with `none`.

## Configuration and operation

The strict schema-v1 JSON loader rejects unknown fields, requires config/password/private-key/provider/secret files to have owner-only permissions with no group/other bits (`0600` is recommended), validates one unambiguous API/Git host/repository identity and minimum polling intervals, and keeps runtime values outside Git. `github.git_host` is accepted only where required for a custom API base. Developer and mandatory Scout URLs must be credential-free loopback HTTP origins with explicit distinct ports; Scout runtime root must be absolute and outside `repository_root`, and its persistence sibling is derived rather than caller-controlled. Provider configuration requires exactly one API-key file or one strictly shaped OpenAI-only OAuth file at the isolated persistent auth location (with bounded legacy-location migration); unknown providers/fields and dual credentials fail closed. Each instance has a unique ID, state path, App mapping, and process lock. Stale locks are recoverable; live duplicate processes are refused. Status distinguishes installation from last endpoint proof.

Normal developer OpenCode, dedicated Scout OpenCode, and the bridge remain portable foreground processes. The tracked developer config relies on OpenCode's current-working-directory defaults for contained work and sets `external_directory` to `ask`; no broad outside-path allow rule exists. Small-developer guidance uses repository-relative paths and rejects parent/sibling rediscovery or scope widening after a missing path. Apply bootstrap installs the external Scout runtime, launches it temporarily, and checks exact installation/version/OpenAPI/agent/model/prompt/permissions/tools before checking/creating ordinary prerequisites. `--check` installs nothing and creates no labels/state but actively launches/probes an existing installation. Bridge startup records Scout failure without aborting developer recovery/control, and later Scout starts retry the independent launch. Bridge service startup still rejects a dirty checkout in addition to a non-`developer` or unsynchronized checkout. Template-development resolution remains lazy, so its absence does not disrupt ordinary developer startup or Scout operation. On termination, the CLI first stops new control-loop polls and waits for the in-flight poll plus all commands/requests it admitted to finish before aborting recovery and exiting; status exposes the drain state. `opencode-attach.sh` still attaches only to normal developer OpenCode.

`scripts/watch-developer-sync.sh` is an optional Linux systemd-user-service helper for a dedicated checkout. A single-instance outbound poll fetches `origin/developer` every configured 5-10 seconds, records status beneath the Git-private bridge directory, and refuses dirty, locally ahead, diverged, wrong-branch, uninspectable, or bridge-active-work states. A behind-only checkout is advanced solely with `merge --ff-only`. Before runtime replacement it asks systemd to stop the bridge through the draining termination path, rechecks Git and durable pending work after stop, then applies and checks bootstrap, verifies the build left the tree clean, and starts the bridge. A private fingerprint over bridge contracts/package plus bootstrap, status, and watcher helpers forces rebuild/recheck when runtime-relevant content changes, including a local synchronized commit that did not require a remote fast-forward; task/document-only commits do not cause an unnecessary restart. The observed installed HEAD is retained separately for diagnostics. Failure leaves source untouched where possible and the bridge stopped after replacement begins rather than running stale or invalid code. No reset, force update, history rewrite, inbound webhook, tunnel, public listener, or force push is used.

The template initializer repairs only complete-history, synchronized clean one-commit unrelated `main`/`developer` roots with matching author/committer identities, author/committer times, subject, and path/mode/type tree shape, plus no active task record. Branch-specific blobs may differ. It creates a local old-root backup ref, then one exact developer-tree-preserving child of main and a hook-validated exact `force-with-lease`. Correct ancestry no-ops; shallow, established, shared, dirty, unsynchronized, active-task, sync-failed, or otherwise ambiguous history is refused; `web-orchestration` is untouched.
